## 1. 定位決策的直接後果

選擇「全景」而非「私人市場觀測站」，會產生三個必須先處理的結構性後果：

### 1.1 需要決定第二套 schema 的策略

政策部門的資料模型與 `GenericHouseItem` 本質不同：

| 維度 | 私部門刊登站（591 等） | 政策部門（社宅招租、包租代管） |
|---|---|---|
| 基本單位 | 持續刊登的物件 | 招租公告／戶別／抽籤梯次 |
| 生命週期 | 上架 → 變動 → 下架（可觀測） | 公告 → 收件 → 抽籤 → 結案（事件流） |
| 價格語意 | 房東開價 | 依所得級距分級的行政訂價 |
| 可得性 | 隨時 | 週期性、批次釋出 |

**這是全景定位的最大單一成本。** 必須在接受第一個政策資料源之前決定走哪條路：

- **方案 A｜擴充 `GenericHouseItem`**：shared enum 大幅擴張，`deal_status` 狀態機需容納「抽籤中／候補」等狀態。優點是單一 pipeline、單一出貨格式；缺點是為了少數 vendor 汙染共用地基，且 enum 編碼值「只能新增、永不改值」的治理原則會讓錯誤決定無法回收。
- **方案 B｜平行 pipeline，出貨端匯合**：政策資料源走獨立的 item schema 與獨立的 spider 基底，僅在 dataset 出貨層以 `sources[]` 併呈。優點是共用地基不受汙染；缺點是兩套測試軌道、兩套哨兵。

**建議：方案 B。** 理由是 §1.1 表格顯示兩者連「基本單位」都不同，強行共用 schema 是把建模錯誤鎖進不可逆的 enum 編碼裡。但這需要維護者拍板，不應由第一個貢獻者的 PR 隱性決定。

### 1.2 架構驗證不能交給政策站

`docs/multi-vendor-plan.md` 的既定原則是「多站抽象由真的要加第二站時驅動」，且「沒有第二個實作者時介面是猜的」。這個原則正確，但有一個前提：**用來驗證抽象的那一站，結構要夠像它未來要服務的多數站。**

若讓一個事件流型的政策站當唯一的 vendor #2，抽出來的介面會是為了容納 outlier 而扭曲的。**建議：架構驗證由一個「與 591 同構的持續刊登站」承擔，政策站平行進行但走方案 B 的獨立軌道。**

### 1.3 排序權重改變

全景定位下，判準的權重需重排：

- **上升**：母體互補性（政策部門與私部門零重疊）、欄位獨特性（合法性認證、弱勢身分別、行政訂價）。
- **下降**：純粹的物件量、與 591 的交叉驗證價值（仍有價值，但不再是首要）。

## 2. 市場結構：三種商業模式決定資料特性

理解這三層可以預測任何一站的資料品質與對抗性，不必逐站試：

| 模式 | 收入來源 | 屋源取得 | 對物件真實性的責任 | 對爬蟲的意涵 |
|---|---|---|---|---|
| 廣告刊登（classified） | 向刊登方收廣告費 | 房東自刊 + 仲介批量上架 | 幾乎不負責 | 量大、重複與幽靈物件多、風控強 |
| 仲介聯賣（MLS 型） | 導流回房仲體系抽佣 | 加盟品牌內部物件庫 | 品牌承擔 | 量小、與 591 仲介刊登高度重疊 |
| 政策媒合（公部門／NPO） | 政府標案、補助、公益資源 | 委外「租屋服務事業」開發 | 有實體訪視與契約審查 | 量小、格式穩定、對抗性低、欄位獨特 |

**推論：廣告模式必然追求物件數極大化並容忍重複；政策模式必然量小且慢但合規欄位完整。** 這解釋了後面所有的量級與物件型態差異。

## 3. 平台盤點

### 3.1 私部門

| 平台 | 量級 | 物件型態偏向 | 對 TWRH 的意涵 |
|---|---|---|---|
| **591 房屋交易網** | 絕對主導 | 全型態：整層住家、獨立套房、分租套房、雅房、店面、辦公、廠房、頂讓 | 已完成，現況基準 |
| **樂屋網 Rakuya** | 中，租屋端遠小於 591 | 整層住家、電梯大樓、仲介代租中高價位；分租套房幾乎缺席 | 邊際資訊量低，延後 |
| **好房網 HouseFun** | 小，媒體屬性已強於交易屬性 | 與 591 重疊為主 | fixture 已預留 pk=2；價值在交叉驗證而非新增物件 |
| **我家網等長尾站** | 宣稱全台逾 12 萬筆不動產物件（含買賣） | 混雜 | 低優先 |
| **聚合器（租租通等）** | 不自營屋源 | 跨站抓取 591／好房網／樂屋網／信義／PTT | 不是資料源，是競品；但可作為「市場痛點是去重不是量」的佐證 |
| **FB 社團／Dcard／PTT／LINE 群** | 成交量被嚴重低估 | 學生分租、找室友、短期轉租、寵物友善、不付廣告費的低價老屋 | **明確排除**（個資與 ToS 紅線、無穩定 schema） |

**591 的補充事實**：2007 年成立，隸屬台灣數字科技（addcn），早期靠大量電視與捷運廣告建立市佔。2026 年已將入口延伸至 LINE MINI App，聚焦搜尋／瀏覽／聯絡，物件諮詢量顯著成長——代表其分發位置正從網站流量轉向通訊軟體內，長期可能影響網頁端的物件完整度，值得列入哨兵觀察假設。

**樂屋網的股權背景**：由 PChome 與信義、中信、住商、太平洋、21 世紀等房仲體系共同成立，本質是仲介聯賣入口而非 C2C 刊登板。這是它租屋量體小、物件型態偏中高價整層的結構原因。

### 3.2 公部門與 NPO

| 資料源 | 量級（已查證） | 物件型態 | 資料模型 |
|---|---|---|---|
| **教育部雲端租屋平臺**（house.nfu.edu.tw） | 全國 200 多所大專校院與高中職 | 學生套房、雅房、分租 | 持續刊登（與 591 同構） |
| **臺北市安心樂租網**（rent.thurc.org.taipei） | 臺北市單一縣市 | 社宅戶別 | 招租公告／抽籤事件流 |
| **社會住宅包租代管**（國土署 → 地方 → 租屋服務事業） | 截至 2026-07 累計協助 116,390 戶，弱勢占 41.19% | 民間閒置住宅，屋齡偏高、零散房東 | 統計數據，無公開物件層資料 |
| **中央社宅招租**（住都中心 HURC） | 分季公告 | 新建電梯大樓 | 公告事件流 |
| **各縣市社宅／包租代管站** | 22 縣市異質系統 | 同上 | 各自為政 |
| **崔媽媽基金會**（rent.tmm.org.tw） | 小 | 弱勢友善屋源：高齡、身障、單親 | 持續刊登 |

**教育部平臺的關鍵特性**（全景定位下最重要的一項）：由教育部委託國立虎尾科技大學研發，全國已有 200 多所學校加入，且**平台內認證合格建物皆經由各校及地方政府完成賃居評核**。這是全台唯一帶實體訪視驗證的全國性租屋物件庫，是 591 結構上不可能擁有的欄位。

**崔媽媽的定位**：1989 年開辦租屋服務中心，是全台第一個也是唯一以住宅租賃服務與租屋市場改革為主軸的 NPO；1994 年開辦租屋法律諮詢，1996 年首創搬家公司評鑑制度，2005 年取得消費者保護團體認定，2013 年催生「蝸牛社會企業」。與 g0v／勞陣同屬居住正義倡議生態圈，**存在「先談再爬」的低成本路徑**。

### 3.3 政策環境中的兩個結構性訊號

這兩項不是資料源，但會改變資料本身，接手時必須知道：

1. **合法性篩選正在收緊**：300 億元中央擴大租金補貼自 115 年（2026）起不再受理無房屋稅籍或未保存登記建築物的新案申請。這會在時間序列上產生**可觀測的結構斷點**——違建與頂加分租供給是否從正式通路退出。以 TWRH 已累積的長期序列，這是少數只有本專案做得出來的分析。
2. **官方租金基準線已存在**：內政部公布 2026 年上半年租金統計，全國租金總價中位數 8,600 元（較上期微增 1.2%），約六成縣市中位數無變動；新成屋租金普遍高於中古屋兩成以上，電梯大樓比公寓貴二至三成。可直接用於哨兵的分佈不變量校準。

## 4. 排序判準

建議把選站變成公開的評分式，寫進 P0 的資料源認領流程，讓提案者自己先算：

```
邊際價值 = 母體互補性 × 生命週期可觀測性 × 欄位獨特性 × 覆蓋廣度
永久成本 = parser 改版頻率 + per-vendor baseline/fixture + 法律與 ToS 風險
優先度  = 邊際價值 / 永久成本 × 認領可信度
```

兩個最容易被低估的項：

- **覆蓋廣度**：一個 parser 能覆蓋幾個縣市／幾所學校／幾個機關。這是成本效益的最大單一變數，且差距可達兩個數量級。
- **欄位獨特性**：該站有沒有 591 結構性缺席的欄位。這比「多幾筆物件」有價值得多。

同時，認領流程的必填欄位應新增「**目的分類**」：架構驗證／資料價值／政策資料。三者的驗收標準不同，混在一起排序會每次重新爭論。

## 5. 排序結果（全景定位）

### 第一順位：教育部雲端租屋平臺（house.nfu.edu.tw）

**同時滿足架構驗證與資料價值，是唯一在兩個目的上都排第一的候選。**

- 覆蓋廣度極高、成本極低：同一套系統的多校 instance，**一個 parser 覆蓋全國 200+ 校**。
- 欄位獨特性最高：賃居評核認證狀態，591 永遠不會有。
- 母體互補：學生分租套房／雅房是 591 覆蓋不完整、弱勢程度高的一段。
- 結構同構：持續刊登型，適合承擔 §1.2 的架構驗證角色。
- 對抗性低：公部門委外系統。

**未驗證，survey 必須回答**：是否需登入才能看物件、robots 與各校自訂條款、資料新鮮度（殭屍刊登比例）、公部門委外系統的個資邊界、各校 instance 的欄位是否一致。

### 第二順位：臺北市安心樂租網（issue #29，已有認領意願）

**接受認領，但重新定位為政策資料源，走 §1.1 方案 B 的獨立軌道。**

- 全景定位下它的價值上升：政策部門的物件層資料目前完全缺席。
- 但它不承擔架構驗證：事件流模型與 `GenericHouseItem` fit 差。
- 需在認領流程中明講定位，避免貢獻者誤解為降級。
- 單一縣市覆蓋是其最大限制；若方案 B 走通，各縣市社宅站可用同一套政策 schema 逐步接入。

**未驗證**：是否需登入（首頁提及收藏物件需登入、採臺北卡 3.0／iSSO 驗證）、公告與戶別資料的結構化程度、歷史公告是否可回溯。

### 第三順位：崔媽媽基金會（fixture 已有 pk=3「蟹居網」）

- 母體與 591 幾乎零重疊，語意價值高（弱勢、高齡、身障屋源）。
- 量小，**爬蟲不是最佳解**：優先嘗試取得資料授權或直接匯出。永久成本可低一個數量級。
- 若走合作路徑，同時打開後續倡議與資料應用的關係鏈。

### 第四順位：包租代管與各縣市社宅（走非爬蟲路徑）

- 22 縣市異質系統，parser 維護成本 N 倍而單站收益低。
- **改走政府資訊公開申請 / 開放資料**：包租代管已有季報制度與統計揭露，物件層資料應以公文申請取得，而非逐站爬。
- 若第二順位的方案 B schema 走通，再評估把資料量最大的二至三個縣市接入。

### 第五順位：好房網（fixture 已有 pk=2）

- 全景定位下降級。價值不在新增物件，而在**交叉驗證**：同一物件在兩站的價格與下架時間差，是目前唯一能量測「幽靈物件率」與「重複刊登率」的方法。
- 但這需要跨站物件模糊比對（地址／坪數／租金），是一整個獨立問題領域。
- **建議獨立立項，不要與 vendor 擴充混排。**

### 延後或排除

| 站別 | 判斷 |
|---|---|
| 樂屋網 | 與 591 仲介刊登高度重疊，邊際資訊量低 |
| 我家網等長尾站 | 同上，且格式不穩 |
| FB 社團／Dcard／PTT | **明確寫入排除清單**：個資與 ToS 紅線，無穩定 schema |
| 品牌公寓／包租代管業者官網 | 站點極度分散、生命週期短、單站覆蓋率低，成本效益最差 |

## 6. 建議的下一步

### 步驟 1：先量測，不要先排序

本文件的排序輸入仍以公開檢索為主，**應被 survey 資料推翻**。P1 既有項「`twrh` CLI 一般化」是這一步的前置：

- [ ] 為 `twrh` 的 `list` / `detail` / `survey` / `probe` 加上 vendor 維度
- [ ] 定義標準化 survey 報告格式，至少涵蓋：
  - 物件總數、日新增量
  - 欄位覆蓋率與空值率
  - 是否有 JSON API 或僅 HTML
  - 是否需登入
  - **生命週期是否可觀測**（同一物件 ID 是否穩定、下架是否可偵測）
  - robots.txt 與服務條款結論
  - 個資邊界（是否含房東姓名、電話、身分資訊）
- [ ] 對教育部雲端租屋、安心樂租網、崔媽媽、好房網各跑一次
- [ ] 依 §4 評分式重排，結果回寫本文件與 `multi-vendor-plan.md`

### 步驟 2：維護者需拍板的決策

- [ ] **§1.1 schema 策略**：方案 A（擴充 `GenericHouseItem`）或方案 B（平行 pipeline）。**建議 B。** 這個決定必須在第一個政策資料源的 parser PR 之前做完，否則會被 PR 隱性決定且不可逆（enum 編碼值只能新增）。
- [ ] **#29 的定位公告**：政策資料源，非 vendor #2 的架構驗證者。
- [ ] **排除清單成文**：FB／Dcard／PTT 寫入 P0 流程文件，避免反覆提案。

### 步驟 3：低成本的資料整合（可與上述平行）

不需要爬蟲、成本近乎零，但直接提升全景完整度：

- [ ] 接入**內政部租金統計與視覺化查詢平臺**，作為哨兵的分佈不變量外部校準來源
- [ ] 評估**租賃實價登錄**（涵蓋率低，僅包租業轉租強制登錄）與 TWRH 刊登價的配對分析——量測「刊登價 vs 成交價」偏離
- [ ] 在時間序列上標記 **115 年租金補貼合法性門檻變更**，設計違建／未保存登記建物供給退出的觀測指標
